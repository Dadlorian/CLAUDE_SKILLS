# Hands-On Lab Assessment Rubric

Comprehensive rubric for evaluating student performance in hands-on lab assignments. Assesses both process and product.

---

## Scoring Scale

**4 - Exemplary**: Exceeds expectations; professional-quality work
**3 - Proficient**: Meets expectations; demonstrates competency
**2 - Developing**: Partially meets expectations; support needed
**1 - Beginning**: Does not meet expectations; significant gaps
**0 - Missing**: Not attempted or fundamentally absent

---

## Assessment Categories

### 1. Technical Implementation (Weight: 30%)

#### 1.1 Functionality & Correctness
**Score 4 - Exemplary**
- All required features implemented and working flawlessly
- Code runs without errors
- Edge cases handled appropriately
- No debugging needed
- Tests pass 100%
- Performance meets or exceeds requirements

**Score 3 - Proficient**
- All required features implemented
- Code runs with minor issues (easily fixed)
- Most edge cases handled
- Tests pass 95%+
- Performance acceptable

**Score 2 - Developing**
- Most features implemented but some incomplete
- Code has bugs requiring debugging
- Limited edge case handling
- Tests pass 70-94%
- Performance issues present

**Score 1 - Beginning**
- Several features missing or broken
- Code has significant errors
- Few edge cases handled
- Tests pass <70%
- Major performance issues

**Score 0 - Missing**
- Work not attempted or non-functional

#### 1.2 Code Quality
**Score 4 - Exemplary**
- Code is clean, readable, and well-organized
- Follows established conventions and best practices
- Appropriate comments and docstrings
- DRY principle applied (no unnecessary repetition)
- Functions have single responsibility
- Variable names are clear and descriptive
- Professional-quality code

**Score 3 - Proficient**
- Code is generally clean and readable
- Follows most conventions
- Adequate comments
- Mostly adheres to DRY
- Functions generally have clear purpose
- Decent variable naming

**Score 2 - Developing**
- Code is somewhat disorganized
- Inconsistent with conventions
- Comments sparse or unclear
- Some code repetition
- Mixed function purposes
- Variable naming could improve

**Score 1 - Beginning**
- Code is difficult to read
- Poor organization
- Few or misleading comments
- Significant code repetition
- Unclear function purposes
- Poor variable naming

**Score 0 - Missing**
- Code not present or incomprehensible

#### 1.3 Error Handling & Validation
**Score 4 - Exemplary**
- Comprehensive input validation
- Graceful error handling throughout
- Meaningful error messages
- Edge cases anticipated and handled
- Defensive programming practices
- Logging/debugging information when appropriate

**Score 3 - Proficient**
- Good input validation
- Error handling in main components
- Generally meaningful error messages
- Most edge cases handled
- Some defensive programming

**Score 2 - Developing**
- Basic validation present
- Error handling incomplete
- Error messages sometimes unclear
- Some edge cases missed
- Limited defensive programming

**Score 1 - Beginning**
- Minimal validation
- Poor error handling
- Unclear error messages
- Many edge cases unhandled
- No defensive programming

**Score 0 - Missing**
- No error handling

## Scoring Calculation

### Step 1: Calculate Category Averages
For each category, average the subcategory scores.

### Step 2: Calculate Weighted Total
```
Total = Σ(Category Average × Weight)

Example:
Technical Implementation: 3.5 × 0.30 = 1.05
Testing & Verification: 3.0 × 0.20 = 0.60
Problem-Solving: 3.0 × 0.15 = 0.45
Documentation: 3.5 × 0.15 = 0.525
Version Control: 3.0 × 0.10 = 0.30

Total: 2.925 ≈ 3.0 (out of 4.0)
```

### Step 3: Convert to Percentage
```
Percentage = (Total / 4.0) × 100
Example: (3.0 / 4.0) × 100 = 75%
```

## Lab-Specific Considerations

### Beginner Labs
- Focus on correctness and functionality
- Documentation and code quality important but secondary
- Testing expectations lower
- Problem-solving approach valued over perfect solution

### Intermediate Labs
- Code quality and testing equally important
- Documentation expectations higher
- Problem-solving and debugging skills assessed
- Some design choices evaluated

### Advanced Labs
- Professional code quality expected
- Comprehensive testing and validation required
- Architectural decisions evaluated
- Innovation and best practices valued
- Performance optimization considered

## Assessment Tips

1. **Run the Code**: Actually execute and test the submission
2. **Check Environment**: Test in appropriate OS/environment
3. **Review Evolution**: Check git history and commits
4. **Time Box**: Don't spend excessive time on any one submission
5. **Be Consistent**: Use rubric consistently across students
6. **Document Issues**: Note specific problems for feedback
7. **Provide Resources**: Suggest how student can improve
8. **Celebrate Success**: Acknowledge good work

---

## Common Issues & Solutions

| Issue | Solution |
|-------|----------|
| Code doesn't run | Request setup instructions; test systematically |
| Incomplete submission | Use rubric as checklist; provide feedback on what's missing |
| Poor documentation | Provide documentation templates and examples |
| Inadequate testing | Discuss testing strategy; provide testing guidelines |
| Messy git history | Provide git best practices guide |
| Copy-paste code | Assess understanding through questions; discuss originality |

---

## Plagiarism Indicators

Watch for:
- Code style inconsistent throughout
- Comments don't match code
- Implementation style changes mid-project
- Solution too similar to published examples
- Student can't explain implementation

**Action**: Discuss with student; use institutional procedures if needed
