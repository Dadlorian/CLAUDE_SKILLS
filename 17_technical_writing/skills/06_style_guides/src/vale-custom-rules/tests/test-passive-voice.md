# Test: Passive Voice Detection

This file is used to test the TechWriter.Passive rule. It identifies passive voice constructions that can make documentation less clear, direct, and actionable. Active voice improves readability and places emphasis on the actor performing the action.

## Rule Purpose

### Why Avoid Passive Voice
Passive voice in technical documentation:
- **Obscures responsibility**: Unclear who performs the action
- **Reduces clarity**: Indirect sentence structure
- **Weakens instructions**: Less imperative and actionable
- **Increases word count**: More verbose than active voice
- **Slows comprehension**: Requires extra mental processing

### When Passive Voice Is Acceptable
- When the actor is unknown or irrelevant
- When emphasizing the object over the subject
- When describing system-generated actions
- In scientific/academic contexts requiring objectivity
- When the passive construction is clearer

## Edge Cases and Acceptable Passive Voice

### State of Being (Acceptable - Not True Passive)
- The API is ready.
- The service is available.
- The server is online.
- The configuration is valid.
- The connection is secure.

**Status:** Should NOT flag - "is" as linking verb, not passive voice
**Reason:** Describes state, not action

### Adjective Predicates (Acceptable)
- The documentation is important.
- The security is critical.
- The performance is excellent.
- The feature is useful.
- The design is intuitive.

**Status:** Should NOT flag - "is" + adjective, not passive construction
**Reason:** No implied action or agent

### System-Generated Actions (Borderline - Context Dependent)
- The email is sent automatically.
- The cache is cleared every hour.
- The logs are rotated daily.
- The data is backed up nightly.
- The metrics are collected continuously.

**Status:** May flag, but acceptable in system documentation
**Reason:** System is the actor, but often implied/obvious
**Better:** "The system sends the email automatically" (if clarity needed)

### When Object Is More Important Than Subject (Acceptable)
- The password is encrypted before storage.
- The token is validated on each request.
- The data is sanitized for security.
- The response is cached for performance.
- The input is normalized before processing.

**Status:** May flag, acceptable when emphasizing the object
**Reason:** Focus on what happens to the object, not who does it
**Alternative:** Could be rewritten if agent adds value

### Unknown or Irrelevant Actor (Acceptable)
- The bug was introduced in version 1.5.
- The feature was deprecated last year.
- The endpoint was removed without notice.
- The library was abandoned by its maintainers.

**Status:** Should flag, but acceptable when actor is unknown/irrelevant
**Reason:** Actor information not available or not useful
**Consider:** Can you identify the actor to make it active?

### Academic/Scientific Style (Context-Dependent)
- The experiment was conducted according to protocol.
- The results were analyzed using statistical methods.
- The data was collected over six months.
- The hypothesis was tested under controlled conditions.

**Status:** May flag, traditional in academic writing
**Guideline:** Technical documentation should still prefer active voice

## Complex Passive Constructions

### Progressive Passive (Should Flag)
- The application is being developed by the team.
- The issue is being investigated by support.
- The feature is being tested by QA.
- The code is being refactored for clarity.

**Active Alternatives:**
- The team is developing the application.
- Support is investigating the issue.
- QA is testing the feature.
- We are refactoring the code for clarity.

### Perfect Passive (Should Flag)
- The server has been configured incorrectly.
- The file has been modified recently.
- The settings have been updated by the admin.
- The connection has been established successfully.

**Active Alternatives:**
- Someone configured the server incorrectly.
- Someone modified the file recently.
- The admin updated the settings.
- The system established the connection successfully.

### Modal Passive (Should Flag)
- The configuration should be verified before deployment.
- The tests must be run after changes.
- The code can be optimized for performance.
- The data might be corrupted.

**Active Alternatives:**
- Verify the configuration before deployment.
- Run the tests after changes.
- You can optimize the code for performance.
- The data might become corrupted.

## Testing Strategy

### Positive Tests (Should Flag as Passive)
1. be/being/been + past participle constructions
2. is/was/were + past participle
3. has/have/had + been + past participle
4. Passive constructions with "by" phrases
5. Passive constructions without agents

### Negative Tests (Should NOT Flag)
1. Active voice sentences
2. Linking verbs with adjectives
3. State-of-being constructions
4. Imperative mood commands
5. Present/past continuous active voice

### Edge Case Tests
1. System-generated actions (context-dependent)
2. Emphasis on object (context-dependent)
3. Unknown actors (context-dependent)
4. Progressive forms ("is running" vs "is being run")
5. Perfect tense active ("has run" vs "has been run")

## Context-Specific Guidelines

### API Documentation
**Avoid Passive:**
- "The request is sent to the endpoint" → "Send the request to the endpoint"
- "Authentication is required" → "You must authenticate"
- "The response is returned as JSON" → "The API returns JSON responses"

**Acceptable Passive:**
- "The API is rate-limited" (system property)
- "Errors are documented below" (focus on errors, not documentor)

### User Guides
**Avoid Passive:**
- "The button can be clicked" → "Click the button"
- "The file should be saved" → "Save the file"
- "Settings can be changed" → "Change the settings"

**Prefer Imperative:**
Direct commands are clearest for instructions

### Release Notes
**Avoid Passive:**
- "Support was added for..." → "We added support for..."
- "The bug was fixed" → "This release fixes the bug"
- "Performance was improved" → "We improved performance"

**Acceptable Passive:**
- "The feature is deprecated" (standard terminology)
- "The API was released in 2023" (historical fact)

### Troubleshooting Guides
**Avoid Passive:**
- "The error is caused by..." → "X causes this error"
- "The issue can be resolved by..." → "Resolve this issue by..."
- "The problem is triggered when..." → "X triggers this problem when..."

**Active Focus:**
Helps users understand cause and solution clearly

## Real-World Examples

### Bad: Installation Instructions
The software should be downloaded from the website. The installer must be run with administrator privileges. The configuration file should be edited before the first launch. The application can be started after installation.

**Issues:** All passive, unclear who performs actions, weak instructions
**Word Count:** 38 words

### Good: Installation Instructions
Download the software from the website. Run the installer with administrator privileges. Edit the configuration file before the first launch. Start the application after installation.

**Improvements:** All active, clear actions, strong commands
**Word Count:** 28 words (26% reduction)

### Bad: API Documentation
Requests are authenticated using API keys. The token is passed in the Authorization header. Data is sent as JSON in the request body. Responses are returned with appropriate status codes.

**Issues:** Passive throughout, unclear responsibilities
**Impact:** Less actionable for developers

### Good: API Documentation
Authenticate requests using API keys. Pass the token in the Authorization header. Send data as JSON in the request body. The API returns responses with appropriate status codes.

**Improvements:** Active voice, imperative mood, clear instructions
**Impact:** Easier to follow, more actionable

### Bad: Error Message
An error was encountered while processing your request. The operation was terminated. Your session was ended due to inactivity. The changes were not saved.

**Issues:** Passive, vague, no clear cause or remedy
**User Experience:** Frustrating, unclear

### Good: Error Message
The system encountered an error while processing your request. We terminated the operation. Your session ended due to inactivity. The system did not save your changes.

**Improvements:** Clear actors, more informative, better UX
**User Experience:** Still bad news, but clearer

## Benefits of Active Voice

### Clarity
- **Passive:** "The bug was fixed" (when? by whom?)
- **Active:** "Version 2.1 fixes the bug" (clear, specific)

### Conciseness
- **Passive:** "The request is validated by the server" (7 words)
- **Active:** "The server validates requests" (4 words, 43% shorter)

### Directness
- **Passive:** "The button should be clicked by the user" (indirect)
- **Active:** "Click the button" (direct command)

### Responsibility
- **Passive:** "An error was made in the configuration" (no accountability)
- **Active:** "You made an error in the configuration" (clear responsibility)

## Common Mistakes to Avoid

1. **Over-Correction:** Not all "be" verbs are passive
2. **Context Ignorance:** Some passive constructions are appropriate
3. **Forced Active:** Don't contort sentences just to avoid passive
4. **Missing Subject:** "To install, the file should be downloaded" (who installs?)
5. **Weak Active:** "The button experiences clicking" (bizarre active construction)
