# Patient Portal Security Guide

## Security Architecture Overview

### Defense in Depth Strategy

```
Layer 1: Network Security
├─ Firewalls (hardware and software)
├─ DDoS protection
├─ Web application firewall (WAF)
└─ Intrusion detection systems

Layer 2: Transport Security
├─ TLS 1.2+ encryption
├─ Strong cipher suites
├─ Certificate pinning (mobile apps)
└─ Perfect forward secrecy

Layer 3: Application Security
├─ Input validation
├─ Output encoding
├─ CSRF protection
├─ XSS prevention
└─ SQL injection prevention

Layer 4: Data Security
├─ Encryption at rest (AES-256)
├─ Tokenization of sensitive data
├─ Secure key management
└─ Hashing and salting

Layer 5: Access Control
├─ Multi-factor authentication
├─ Role-based access control
├─ Least privilege principle
└─ Session management

Layer 6: Monitoring and Detection
├─ Real-time threat detection
├─ Anomaly detection
├─ Audit logging
└─ Security information and event management (SIEM)
```

## Authentication Implementation

### Multi-Factor Authentication (MFA) Options

**Option 1: SMS-Based OTP**
- Send one-time password via SMS
- Valid for 5-10 minutes
- User enters code to complete login
- Least secure but accessible to all

**Option 2: TOTP (Time-Based OTP)**
- Time-based one-time password
- Generated by authenticator apps (Google Authenticator, Authy)
- 30-second window validity
- More secure, user-friendly

**Option 3: Security Questions**
- Pre-configured knowledge-based questions
- Answers hashed and stored securely
- Backup authentication method
- Should not be only MFA

**Option 4: Biometric Authentication**
- Fingerprint recognition
- Face recognition (FaceID, Windows Hello)
- Highly secure, convenient
- Requires compatible devices

### Session Management

```
Recommended Configuration:
├─ Session timeout: 15 minutes of inactivity
├─ Absolute session timeout: 8 hours
├─ Token refresh: Allow refresh within 7 days
├─ Device tracking: Track and restrict devices
├─ Concurrent sessions: Limit to 2-3 active sessions
└─ Logout: Invalidate all sessions on logout
```

## Data Encryption Standards

### Encryption at Rest

**Database Encryption:**
```sql
-- Enable database-level encryption
CREATE TABLE patient_data (
  id INT PRIMARY KEY,
  ssn VARCHAR(11) ENCRYPTED WITH (ENCRYPTION_TYPE = DETERMINISTIC),
  medical_record BLOB ENCRYPTED WITH (ENCRYPTION_TYPE = RANDOMIZED),
  ...
);

-- Use AES-256 for all sensitive fields
```

**File Storage Encryption:**
- Encrypt all uploaded documents
- Separate encryption key per document
- Use AWS S3 with server-side encryption
- Or use Azure Blob Storage encryption

### Encryption in Transit

**TLS Configuration:**
```nginx
# nginx configuration
server {
  listen 443 ssl http2;
  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_ciphers HIGH:!aNULL:!MD5;
  ssl_prefer_server_ciphers on;
  ssl_certificate /path/to/cert.pem;
  ssl_certificate_key /path/to/key.pem;

  # Enable HSTS
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}
```

## Access Control and Authorization

### Role-Based Access Control (RBAC)

```
Patient Role:
├─ View own health information
├─ Request prescription refills
├─ Schedule/reschedule appointments
├─ Send secure messages
├─ Download health records
└─ Cannot access other patients' data

Provider Role:
├─ View assigned patients
├─ Document clinical notes
├─ Order tests and procedures
├─ Prescribe medications
└─ View audit logs

Administrator Role:
├─ Manage user accounts
├─ Configure system settings
├─ View compliance reports
├─ Manage access controls
└─ Monitor security events

System Administrator:
├─ Full system access
├─ Database management
├─ Server administration
├─ Incident response
└─ Backup and recovery
```

### Attribute-Based Access Control (ABAC)

```python
# Example: Patient can view labs only within 30 days if ordered by their provider
access_policy = {
  'resource': 'lab_results',
  'subject': 'patient',
  'conditions': {
    'time_since_order': '<30 days',
    'ordered_by_provider': 'in_care_team',
    'test_type': 'not in restricted_list'
  },
  'action': 'view'
}
```

## Audit Logging Requirements

### What to Log

```
Every Access Event Must Include:
├─ User ID (anonymized for queries)
├─ Timestamp (UTC)
├─ IP address
├─ Action performed
├─ Resource accessed (patient ID, record type)
├─ Success/failure status
├─ Duration of access
└─ Data elements viewed/modified

Sensitive Event Logging:
├─ Failed login attempts
├─ Privilege escalation attempts
├─ Mass data downloads/exports
├─ Account modifications
├─ Permission changes
├─ Encryption key access
└─ Administrative actions
```

### Log Analysis and Monitoring

**Real-Time Alerts:**
```
Alert if:
├─ 5 failed login attempts in 5 minutes
├─ Access to 100+ patient records within 1 hour
├─ Off-hours access by healthcare worker
├─ Export of large datasets
├─ Access from unusual geographic location
└─ Database direct query attempts
```

**Regular Log Review:**
- Daily: Failed authentication attempts
- Weekly: Unusual access patterns
- Monthly: Comprehensive audit report
- Quarterly: Audit trail verification

## Mobile Security

### Mobile App Security

**Requirements:**
```
iOS:
├─ Code signing
├─ Entitlements configuration
├─ Secure enclave usage
├─ Certificate pinning
└─ App Transport Security

Android:
├─ Signed APK
├─ ProGuard obfuscation
├─ Secure coding practices
├─ Hardware-backed keystore
└─ Network security config
```

**Data Storage:**
```
Never Store (in plaintext):
├─ Passwords
├─ Tokens/API keys
├─ SSN or medical ID
├─ Complete credit cards
└─ PHI

Acceptable with Encryption:
├─ Session tokens (encrypted)
├─ Cached records (encrypted)
├─ Offline data (encrypted)
└─ Device identifiers
```
