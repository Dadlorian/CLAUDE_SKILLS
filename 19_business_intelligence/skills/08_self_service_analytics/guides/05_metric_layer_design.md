# Metric Layer Design Guide

## Why Metric Layer?

**Problem**: Same metric calculated 10 different ways across dashboards
**Solution**: Single source of truth for all metrics
**Result**: Consistency, trust, efficiency

## Implementation Approach

### Option 1: dbt Metrics (Recommended for dbt users)

```yaml
# dbt_project.yml
metrics:
  - name: monthly_recurring_revenue
    label: Monthly Recurring Revenue (MRR)
    model: ref('fct_subscriptions')
    description: Sum of active subscription amounts

    calculation_method: sum
    expression: subscription_amount

    timestamp: subscription_date
    time_grains: [day, week, month, quarter, year]

    dimensions:
      - subscription_tier
      - customer_segment
      - region

    filters:
      - field: subscription_status
        operator: '='
        value: "'active'"
      - field: is_trial
        operator: '='
        value: 'false'

    meta:
      owner: finance_analytics_team
      certification: verified
```

### Option 2: LookML (Looker)

```lookml
view: subscriptions {
  sql_table_name: fct_subscriptions ;;

  measure: monthly_recurring_revenue {
    label: "MRR"
    description: "Sum of active subscription amounts"
    type: sum
    sql: ${TABLE}.subscription_amount ;;
    filters: [
      subscription_status: "active",
      is_trial: "false"
    ]
    value_format_name: usd
    drill_fields: [subscription_detail*]
  }

  dimension: subscription_tier {
    type: string
    sql: ${TABLE}.tier ;;
  }
}
```

### Option 3: Cube.js (API-first)

```javascript
cube('Subscriptions', {
  sql: `SELECT * FROM fct_subscriptions`,

  measures: {
    mrr: {
      sql: `subscription_amount`,
      type: `sum`,
      description: 'Monthly Recurring Revenue',
      filters: [
        { sql: `${CUBE}.subscription_status = 'active'` },
        { sql: `${CUBE}.is_trial = false` }
      ]
    }
  },

  dimensions: {
    tier: {
      sql: `tier`,
      type: `string`
    },
    date: {
      sql: `subscription_date`,
      type: `time`
    }
  },

  preAggregations: {
    main: {
      measures: [mrr],
      dimensions: [tier],
      timeDimension: date,
      granularity: `day`
    }
  }
});
```

## Metric Definition Template

```yaml
Metric: customer_lifetime_value
Label: Customer Lifetime Value (LTV)
Owner: customer_analytics_team@company.com

Description: >
  Total revenue generated by a customer over their entire
  relationship with the company.

Calculation: SUM(order_amount) per customer
SQL: SELECT customer_id, SUM(order_amount) as ltv
     FROM orders
     GROUP BY customer_id

Dimensions:
  - acquisition_channel
  - customer_segment
  - signup_cohort

Filters:
  - order_status = 'completed'

Grain: customer_id
Aggregation: sum (to get total LTV across customers)

Related Metrics:
  - customer_acquisition_cost (CAC)
  - ltv_to_cac_ratio
  - average_order_value

Known Limitations:
  - Only includes completed orders
  - Does not account for returns
  - Historical data before 2020 incomplete

Certification: Verified
Last Updated: 2025-11-15
Change Log:
  - 2025-11-15: Added filter for completed orders only
  - 2025-10-01: Initial definition
```

## Best Practices

```yaml
Naming Conventions:
  Format: [domain].[entity].[metric]
  Examples:
    - finance.revenue.mrr
    - product.users.dau
    - marketing.acquisition.cac

Documentation:
  Required:
    - Clear description
    - Calculation logic
    - Owner
    - Certification status

  Nice-to-have:
    - Example query
    - Related metrics
    - Known limitations
    - Change history

Versioning:
  Approach 1: Version suffix
    - mrr_v1, mrr_v2

  Approach 2: Effective dating
    - mrr (always current)
    - effective_from: 2025-01-01
    - previous_version: archived

Testing:
  - Known values test
  - Historical comparison
  - Edge cases
  - Performance benchmarks
```
