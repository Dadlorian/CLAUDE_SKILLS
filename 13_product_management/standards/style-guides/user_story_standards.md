## Overview

User stories are a tool for capturing product requirements from the user's perspective. They shift focus from what the system does to why users need a feature. This standard ensures user stories are clear, testable, and implementable across all product teams.

**Purpose**: Facilitate communication between product, engineering, and design by describing features from the user's point of view

**Audience**: Product managers, engineers, designers, QA, stakeholders

**Key Benefits**:
- Maintains focus on user value rather than technical implementation
- Creates shared understanding across disciplines
- Facilitates breaking down work into manageable increments
- Provides criteria for testing and acceptance
- Documents product decisions and reasoning

## What Makes a Good User Story

### The INVEST Principles

Good user stories follow the INVEST criteria:

**I - Independent**
- Story can be developed independently
- Minimal dependencies on other stories
- Not split across multiple sprints
- If dependencies exist, clearly document them

**N - Negotiable**
- Details are open for discussion and refinement
- Not a detailed specification, but a promise of conversation
- Team can discuss and adjust implementation approach
- Acceptance criteria are negotiable until commitment

**V - Valuable**
- Delivers clear value to users or business
- "Why does this matter?" is answerable
- Can be released independently and provide benefit
- Prioritization makes sense with clear value statement

**E - Estimable**
- Engineering team can estimate effort
- Not so vague that estimation is impossible
- Sufficient detail provided for sizing
- Dependencies and unknowns are identified

**S - Small**
- Can be completed in a single sprint
- Typically 1-10 days of work (size-dependent)
- If larger, break into multiple stories
- Small enough for meaningful progress daily

**T - Testable**
- Acceptance criteria are specific and verifiable
- Team can definitively say when story is done
- No ambiguous criteria like "improve performance"
- Testing approach is clear

### User Story Characteristics

**Clear User Focus**
- Written from the perspective of the end user
- Explains what benefit the user gets
- Focuses on the "why" not the "what"

**Specific and Concrete**
- Not vague or abstract ("improve the experience")
- Includes concrete scenarios and examples
- Defined scope that's achievable

**Independent**
- Self-contained with minimal cross-dependencies
- Can be developed without waiting for other work
- Related stories grouped but not dependent

**Completable**
- Achievable within a single iteration/sprint
- Team has skills to complete
- Resources available to finish
- No external blockers

**Testable**
- Clear criteria for successful completion
- QA can verify story is done
- Success criteria are specific and measurable
- Edge cases are documented

## User Story Structure

### Basic Format

```
As a [user type/persona],
I want to [action/capability],
So that [benefit/reason].

Acceptance Criteria:
- [Specific, testable criterion]
- [Specific, testable criterion]
- [Specific, testable criterion]

Definition of Done:
- [Code reviewed and merged]
- [Unit tests written and passing]
- [Manual testing completed]
- [Documentation updated]
```

### Component Breakdown

#### 1. User Story Header

**Template**:
```
[Story ID] - [Story Title]
Epic: [Epic Name]
Sprint: [Sprint Number]
Complexity: [S/M/L/XL]
```

**Guidelines**:
- Story ID: Auto-generated by system (e.g., PROD-1234)
- Title: Concise (8-10 words), describes end-user capability
- Title Format: "Verb + Noun" or "User + Capability"
- Epic: Link to larger initiative
- Complexity: Relative sizing (Small/Medium/Large/X-Large)

**Examples**:
- PROD-1204: Allow users to export data to CSV
- PROD-1205: Enable dark mode toggle in settings
- PROD-1206: Restrict API access by IP whitelist

#### 2. User Story Description

**Structure**:
```
As a [user type/persona],
I want to [action or feature],
So that [business value or reason].
```

**User Type/Persona** (Who)
- Be specific: "Sales representative" not "user"
- Reference defined personas if available
- Examples:
  - "As a data analyst,"
  - "As an enterprise account manager,"
  - "As a new free-tier user,"
  - "As a product manager reviewing team performance,"

**Action/Capability** (What)
- Describe what user wants to do
- Focus on user action, not system behavior
- Avoid technical implementation details
- Examples:
  - "I want to filter results by date range"
  - "I want to see how my team is performing"
  - "I want to bulk export all customer data"
  - "I want to set up SSO authentication"

**Business Value/Reason** (Why)
- Articulate the benefit to the user
- Explain the problem being solved
- Justify why this matters
- Examples:
  - "so I can quickly find relevant information"
  - "so I can make data-driven decisions about resource allocation"
  - "so I can comply with our data governance requirements"
  - "so we can reduce onboarding time for enterprise customers"

**Example User Stories**:

```
As an enterprise sales representative,
I want to see real-time pipeline opportunities,
So that I can prioritize high-value deals and meet quota.
```

```
As a product analytics team member,
I want to export custom reports in multiple formats (CSV, PDF, JSON),
So that I can share insights with stakeholders who prefer different file types.
```

```
As a new free-tier user,
I want an interactive onboarding tutorial,
So that I can understand core features without reading documentation.
```

#### 3. Acceptance Criteria

**Definition**: Specific conditions that must be met for the story to be considered done

**Format**: Gherkin-style "Given/When/Then" or simple checklist

**Gherkin Format**:
```
Given [initial context/state]
When [user performs action]
Then [expected outcome]
```

**Checklist Format**:
```
□ [Specific, verifiable condition]
□ [Specific, verifiable condition]
□ [Specific, verifiable condition]
```

**Rules for Acceptance Criteria**:
- Each criterion must be testable and binary (done or not done)
- Include happy path and edge cases
- Avoid vague terms: "good", "proper", "efficient"
- Be specific about thresholds: "loads in < 2 seconds" not "loads quickly"
- Include edge cases and error scenarios
- Maximum 3-5 core criteria per story (more indicates story is too large)

**Example Acceptance Criteria**:

```
Story: Allow users to filter results by date range

Acceptance Criteria:
□ Date range picker appears in filter panel
□ User can select start date and end date
□ Results update in real-time as dates change
□ Selecting a past date and future date works correctly
□ Hitting "reset" clears date filter and shows all results
□ Date picker remembers last used range (during session)
□ Error message shows if end date is before start date
□ Filter works with timezone offsets (show in user's timezone)
```

**Example Gherkin Format**:

```
Story: Dark mode toggle in settings

Scenario: User enables dark mode
Given the user is in Settings > Appearance
When the user clicks "Dark Mode" toggle to ON
Then the application immediately switches to dark theme
And the setting is saved to user preferences
And dark mode persists across sessions

Scenario: Dark mode respects system preference
Given the user has not manually set dark mode preference
When the system's OS is in dark mode
Then the application displays in dark theme by default
```

#### 4. Definition of Done

**What is it**: Checklist of tasks that must be completed for story to be production-ready

**Standard Definition of Done** (applies to all stories):
- [ ] Code written and committed to feature branch
- [ ] Code review completed and approved by peer
- [ ] Unit tests written (minimum 80% coverage of new code)
- [ ] All tests passing in CI/CD pipeline
- [ ] Manual testing completed against acceptance criteria
- [ ] No console errors or warnings
- [ ] No new security vulnerabilities introduced
- [ ] Documentation updated (if applicable)
- [ ] Product manager approval obtained
- [ ] Merged to main branch
- [ ] Story updated with actual time spent

**Story-Specific Definition of Done** (add when applicable):
- [ ] User testing completed (for UX-heavy stories)
- [ ] Analytics instrumentation added
- [ ] Email/communication template created
- [ ] Help documentation updated
- [ ] Database migrations reviewed
- [ ] Performance testing completed
- [ ] Accessibility audit passed
- [ ] Mobile responsiveness verified

#### 5. Story Metadata

```
Priority: [Critical / High / Medium / Low]
Story Points: [1 / 2 / 3 / 5 / 8 / 13]
Epic Link: [Epic ID and name]
Parent Story: [If part of larger decomposition]
Related Stories: [Other related stories]
Depends On: [Dependencies]
Blocked By: [Current blockers]
Created: [Date]
Updated: [Date]
Owner: [Product Manager Name]
Stakeholders: [Teams/people affected]
```

```markdown
So that [business value].

## Acceptance Criteria

□ [Criterion 1 - specific and testable]
□ [Criterion 2 - specific and testable]
□ [Criterion 3 - specific and testable]
```

```markdown
**Proposed Solution**:
[Technical approach]

- Performance improvement: [Quantified if possible]
- Scalability improvement: [How?]
- Reliability improvement: [What failures prevented?]

- Unit tests: [What to test]
- Integration tests: [What to test]
- Load tests: [What to measure]

## Definition of Done

- [ ] Code reviewed by tech lead
- [ ] Technical design document reviewed

- [ ] Database migrations (if applicable) tested

```

### Template 3: Spike / Investigation Story

```markdown
# [STORY-ID] - [Investigation Title]

**Type**: Spike
**Goal**: [What question are we trying to answer?]
**Timebox**: [Maximum hours/days for investigation]

## Description

We need to investigate [topic] to determine [question].

## Acceptance Criteria

For this spike to be complete, we will:
□ Research [specific area]
□ Create proof of concept for [specific approach]
□ Document findings in [location]
□ Present recommendation to [team]

## Definition of Done

- [ ] Findings documented
- [ ] Team discussion completed
- [ ] Follow-up stories created based on findings
- [ ] Decision made on how to proceed

1. [Key question 1]
2. [Key question 2]
3. [Key question 3]
```

## Acceptance Criteria Guidelines

### Writing Effective Acceptance Criteria

#### Rule 1: Be Specific and Measurable

**Weak**: "User can filter data"
**Strong**: "User can filter by date range (start date and end date) and filter results update within 500ms"

**Weak**: "Performance is improved"
**Strong**: "Page load time decreased from 3s to < 1s for 95th percentile"

#### Rule 2: Include Edge Cases

**Story**: Allow users to set custom discount codes

**Acceptance Criteria**:
- [ ] User can create a discount code with alphanumeric characters
- [ ] Discount code length is limited to 10 characters
- [ ] System prevents duplicate discount codes
- [ ] Special characters (!, @, #) are not allowed, shows error message
- [ ] Empty discount code shows validation error
- [ ] User can edit existing discount code details
- [ ] Discount code can be disabled without deletion

#### Rule 3: Define Error Scenarios

**Story**: Transfer user account to different email address

**Acceptance Criteria**:
- [ ] Form shows validation error if new email already exists in system
- [ ] Form shows validation error if new email format is invalid
- [ ] Confirmation email is sent to new email address
- [ ] User must click confirmation link to complete transfer
- [ ] Clicking invalid/expired link shows helpful error message
- [ ] User can cancel transfer within 24 hours
- [ ] After transfer, old email cannot be used to log in

#### Rule 4: Account for Different Users/Contexts

**Story**: Users can view team members' availability

**Acceptance Criteria**:
- [ ] Team lead can see all team members' availability
- [ ] Individual team members can see their own availability
- [ ] Individual team members cannot see other team members' detailed schedule
- [ ] System displays "unavailable" if user has marked themselves as such
- [ ] Availability updates in real-time
- [ ] Time zone differences are respected
- [ ] Guest/external users see only public availability

#### Rule 5: Link to Design/Mockups When Appropriate

**Story**: Redesign profile page layout

**Acceptance Criteria**:
- [ ] Profile information displays in [3-column layout per design_v2.png](link)
- [ ] Profile photo loads in < 1 second
- [ ] Edit button appears for user's own profile (not others' profiles)
- [ ] Page is responsive on mobile (stacks to single column)
- [ ] All text is readable with WCAG AA color contrast standards
- [ ] Form validation appears as per [form_error_spec.md](link)

### Acceptance Criteria Anti-Patterns

**Anti-Pattern 1**: Vague Success Criteria

Wrong: "The feature works well"
Right: "Feature loads without errors in Chrome, Firefox, Safari, Edge on desktop and mobile"

**Anti-Pattern 2**: Implementation Details

Wrong: "Use Redis caching to improve lookup performance"
Right: "User lookup returns results in < 100ms (previously 2s)"

**Anti-Pattern 3**: Unmeasurable Criteria

Wrong: "Improve user experience"
Right: "Reduce page load time to < 1s (measured via Google Analytics)"

**Anti-Pattern 4**: Multiple Acceptance Criteria Hiding Multiple Stories

Wrong: "Users can manage accounts, change passwords, set up 2FA, and view activity logs"
Right: [Split into 4 separate stories]

**Anti-Pattern 5**: Criteria That Are Always True

Wrong: "Code is tested" (this is part of Definition of Done)
Right: "Feature works with 10,000+ records without performance degradation"

## Story Mapping and Decomposition

### When to Decompose a Story

Stories should be decomposed if they:
- Cannot be completed in one sprint
- Require multiple skill sets (design, backend, frontend)
- Have multiple distinct user flows
- Would require > 13 story points

### Decomposition Patterns

#### Pattern 1: By User Flow Step

**Large Story**: Users can complete end-to-end onboarding

**Decomposed**:
1. Step 1: Users can sign up with email/password (3 points)
2. Step 2: Users can set up workspace and team (5 points)
3. Step 3: Users can invite team members (3 points)
4. Step 4: Users can configure integrations (8 points)

#### Pattern 2: By Technical Layer

**Large Story**: Build notification system

**Decomposed**:
1. Create notification database schema and API (5 points)
2. Add notification UI components (5 points)
3. Integrate notifications with feature actions (3 points)
4. Set up notification queue and delivery system (8 points)
5. Add user notification preferences settings (3 points)

#### Pattern 3: By User Type/Segment

**Large Story**: Sales team can manage their pipeline

**Decomposed**:
1. Sales reps can view opportunities assigned to them (5 points)
2. Sales managers can view team pipeline and forecasts (8 points)
3. Sales admin can configure custom pipeline stages (5 points)

#### Pattern 4: By Platform/Device

**Large Story**: Users can access dashboard on any device

**Decomposed**:
1. Dashboard responsive on desktop (5 points)
2. Dashboard responsive on tablet (3 points)
3. Mobile app native dashboard view (8 points)

#### Pattern 5: Spike Then Implementation

**Large Story**: Integrate third-party analytics service

**Decomposed**:
1. [Spike] Investigate third-party analytics options (8 hours, timebox)
2. Implement selected analytics integration (5 points)
3. Create analytics dashboard (5 points)
4. Add event tracking to key user flows (3 points)

## Real Examples

### Example 1: Consumer Product Feature

```markdown
# PROD-2104 - Save articles to reading list

**Epic**: Content Consumption Experience
**Priority**: High
**Story Points**: 5
**Owner**: Sarah Chen

## Description

As a content consumer,
I want to save articles to a reading list,
So that I can access them later without losing them.

## Acceptance Criteria

□ User sees "Save" button on article page
□ Clicking "Save" shows confirmation toast: "Article saved to reading list"
□ User can view reading list from navigation menu
□ Reading list shows article title, date, and preview image
□ User can remove article from reading list (with confirmation)
□ Reading list persists across browser sessions
□ Reading list is synced across user's devices
□ User can mark articles as "Read" in reading list
□ Reading list shows total number of saved articles
□ Unsaved articles show "Save" button; saved articles show "Remove" button

## Definition of Done

- [ ] Code reviewed and approved by frontend lead
- [ ] Unit tests written (>80% coverage)
- [ ] Manual testing completed on Chrome, Firefox, Safari
- [ ] Mobile responsiveness verified
- [ ] Analytics tracking added for save/remove events
- [ ] Product manager approval obtained
- [ ] Merged to main branch

## Technical Notes

**Storage**: Use Firebase Realtime Database for sync across devices
**API Endpoint**: POST /api/articles/:id/save, DELETE /api/articles/:id/save

## Analytics

- Track: "article_saved" event with article_id, timestamp
- Track: "article_removed_from_list" event
- Measure: % of articles saved vs. viewed (engagement metric)
```

### Example 2: Enterprise B2B Feature

```markdown
# PROD-2234 - Enable single sign-on (SSO) via SAML

**Epic**: Enterprise Security and Compliance
**Priority**: Critical
**Story Points**: 13
**Owner**: Michael Rodriguez

## Description

As an enterprise security administrator,
I want to configure SAML-based single sign-on for my organization,
So that I can enforce corporate identity management and reduce password management burden.

## Acceptance Criteria

Given an enterprise customer with SAML identity provider
When they configure SAML metadata and endpoints in admin console
Then users can log in via their corporate SSO

□ Admin can upload SAML metadata file (XML)
□ Admin can manually enter SAML endpoints if file unavailable
□ System validates SAML configuration before saving
□ Users see "Sign in with SSO" option on login page
□ Users are redirected to corporate identity provider for authentication
□ After successful authentication, user is logged into application
□ New users from SSO are automatically created with correct permissions
□ Existing users can link their account to SSO identity
□ Admin can disable/enable SSO without losing configuration
□ SAML response validation prevents unauthorized access
□ User attributes (email, name) are synced from identity provider
□ Audit log records all SSO configuration changes
□ Error messages guide admin if SAML configuration is incorrect

## Definition of Done

- [ ] SAML integration library selected and tested
- [ ] Security review completed by infosec team
- [ ] Code reviewed by backend lead
- [ ] Unit tests written (>90% coverage for security code)
- [ ] Integration tests verify SAML flow with test IdP
- [ ] User testing with enterprise customer completed
- [ ] Documentation created for admin setup
- [ ] Deployment plan reviewed
- [ ] Merged to main branch
- [ ] Customer success team trained on SAML support

## Technical Details

**Framework**: Use SAML2 specification
**Library**: Consider python-saml or similar
**Storage**: SAML config stored encrypted in database
**Testing**: Test with Okta and Azure AD test environments

## Compliance

- Meets SOC 2 requirement for SSO support
- SAML assertions must be encrypted and signed

## Related Stories

- PROD-2235: Admin can manage user access levels via SAML groups
- PROD-2236: Audit log shows SSO login attempts

## Risks

- SAML configuration complexity could confuse admins
- Mitigation: Provide admin documentation with screenshots and video
```

### Example 3: Mobile App Feature

```markdown
# PROD-2456 - Biometric authentication (Face ID / Touch ID)

**Epic**: Mobile Experience Enhancement
**Priority**: High
**Story Points**: 8
**Owner**: Priya Patel

## Description

As a mobile app user,
I want to use my phone's biometric authentication to log in,
So that I can access the app quickly without typing my password.

## Acceptance Criteria

□ First time user is prompted to enable biometric auth
□ User can toggle biometric auth on/off in settings
□ When biometric auth is enabled, app uses Face ID or Touch ID on launch
□ Biometric authentication fails gracefully with fallback to password
□ Failed biometric attempt (3x) locks out biometric auth temporarily
□ Successful biometric auth logs user in within 2 seconds
□ Biometric credentials are stored securely in device keychain
□ User is prompted to re-authenticate biometrically after 7 days of inactivity
□ Disabling biometric auth requires entering password
□ App handles device with no biometric hardware (shows only password option)
□ Works on iOS (Face ID / Touch ID) and Android (fingerprint / face)
□ Biometric auth is disabled if device has untrustworthy lockscreen

## Definition of Done

- [ ] Code reviewed by security engineer and mobile leads
- [ ] Unit tests written for authentication logic
- [ ] Device testing on iPhone and Android phones (multiple models)
- [ ] Security review completed (biometric storage, fallback handling)
- [ ] User testing completed with 10+ beta users
- [ ] Analytics added to track adoption rate
- [ ] Help documentation updated with setup instructions
- [ ] Merged to main branch

## Technical Notes

**iOS**: Use LocalAuthentication framework (Face ID / Touch ID)
**Android**: Use BiometricPrompt API
**Security**: Use device keychain for credential storage, never store in app

## Analytics

- Track: "biometric_auth_enabled" event
- Track: "biometric_auth_success" event
- Track: "biometric_auth_failed" event
- Measure: % of daily active users using biometric auth

## Device Support

Minimum OS versions: iOS 12.0+, Android 9.0+
```

## Common Mistakes

### Mistake 1: Story is Too Large

**Problem**: Story takes 20+ story points, cannot complete in one sprint

**Example**: "Users can create and manage entire project workspace"

**Solution**: Decompose into smaller stories:
- Users can create new workspace (5 points)
- Users can rename workspace (2 points)
- Users can add team members to workspace (3 points)
- Users can configure workspace settings (3 points)

### Mistake 2: Acceptance Criteria Are Vague

**Problem**: QA cannot determine if story is done

**Bad AC**: "System should be robust"
**Good AC**: "System handles 1000+ concurrent users without error rate exceeding 0.1%"

**Bad AC**: "User can view their data"
**Good AC**: "User can view their data filtered by date range (start/end dates), sorted by any column, exported to CSV/PDF"

### Mistake 3: Story Mixes Multiple User Types

**Problem**: Story tries to cover different user workflows

**Bad**: "Users can collaborate on projects"
**Good**:
- PROD-X: Team members can comment on project deliverables
- PROD-Y: Project managers can assign tasks to team members
- PROD-Z: Stakeholders can view read-only project status

### Mistake 4: Acceptance Criteria Include Implementation Details

**Problem**: Constrains engineering solution unnecessarily

**Bad**: "System uses Redis cache to improve lookup performance"
**Good**: "User lookup returns results in < 100ms (currently 2 seconds)"

### Mistake 5: Missing "Why" in User Story

**Problem**: Team doesn't understand business value

**Bad**: "As a user, I want to export data in CSV format"
**Good**: "As a data analyst, I want to export data in CSV format, so I can analyze it in Excel without manual formatting"

### Mistake 6: Story Cannot Be Tested

**Problem**: QA cannot verify story is actually done

**Bad**: "Feature is well integrated with existing system"
**Good**: "When importing data, the system validates all 500+ required fields and shows specific error message for each invalid field"

### Mistake 7: No Clear Definition of Done

**Problem**: Story lingers in "done" limbo, never merged or deployed

**Solution**: Always include Definition of Done checklist with specific tasks

## Do's and Don'ts

### DO's

- **DO** write from user perspective: focus on "why" not "what"
- **DO** include specific, measurable acceptance criteria
- **DO** ensure story can be completed in one sprint
- **DO** get team agreement on story size before starting
- **DO** include relevant context: links to mockups, PRDs, design docs
- **DO** define edge cases and error scenarios in acceptance criteria
- **DO** include clear Definition of Done
- **DO** link related stories and dependencies
- **DO** assign to specific person/owner
- **DO** use specific, concrete language (avoid "sometimes", "usually")
- **DO** include priority and business value
- **DO** document open questions for team discussion
- **DO** test acceptance criteria are actually verifiable
- **DO** use consistent formatting and terminology
- **DO** include data/examples where helpful

### DON'Ts

- **DON'T** write technical specifications instead of user stories
- **DON'T** include implementation details in story description
- **DON'T** create stories that span multiple sprints
- **DON'T** use vague acceptance criteria ("works correctly", "user-friendly")
- **DON'T** cover multiple user types in one story without decomposition
- **DON'T** forget the "why" (the So That clause)
- **DON'T** mix multiple features into single story
- **DON'T** write acceptance criteria that are impossible to test
- **DON'T** make acceptance criteria that state the obvious
- **DON'T** leave stories without clear priority
- **DON'T** assume context that only one person knows
- **DON'T** create stories without discussing with team first
- **DON'T** forget about non-happy-path scenarios
- **DON'T** use acronyms without explanation (even if internal)
- **DON'T** create stories that are blocked and have no workaround

### Common Writing Anti-Patterns

**Anti-Pattern**: Starting with "System should..."

Wrong: "As a user, the system should send notification emails"
Right: "As a user, I want to receive email notifications when someone mentions me, so I don't miss important conversations"

**Anti-Pattern**: Feature-focused instead of user-focused

Wrong: "Build dark mode"
Right: "As a user, I want to enable dark mode in settings, so I can reduce eye strain when using the app at night"

**Anti-Pattern**: Missing quantification

Wrong: "Page should load quickly"
Right: "Dashboard should load in under 1 second (measured at 95th percentile)"

**Anti-Pattern**: Confusing acceptance criteria with tasks

Wrong Acceptance Criteria:
- [ ] Design mockups created
- [ ] Code review scheduled
- [ ] QA testing plan prepared

Right Acceptance Criteria:
- [ ] User can perform [action] and see [result]
- [ ] System validates [input] with [specific error message]
- [ ] Performance meets [specific metric]

## Story Refinement Checklist

Before story is considered "ready for development":

- [ ] Title is clear and concise
- [ ] User story description is complete (As a... I want... So that...)
- [ ] All acceptance criteria are specific and testable
- [ ] Story can be completed in one sprint
- [ ] Team can estimate the story
- [ ] All dependencies are documented
- [ ] Design/wireframe attached if applicable
- [ ] Analytics requirements documented
- [ ] Definition of Done is clear
- [ ] Business value is clear
- [ ] Priority is set
- [ ] Related/dependent stories are linked
- [ ] All team members understand the story
- [ ] No open questions remain (or documented for discussion)
- [ ] Story has owner assigned
- [ ] Acceptance criteria are reviewed and approved by PM

---

**Quick Tip**: A well-written user story should answer these questions:
1. WHO is using the feature? (persona/user type)
2. WHAT do they want to do? (action)
3. WHY do they want to do it? (benefit/business value)
4. HOW will we know it's done? (acceptance criteria)
5. WHEN should it be complete? (priority, sprint)
