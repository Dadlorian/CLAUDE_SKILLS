# Session Persistence Configuration
# Cookie-based, IP Hash, and Distributed Session Store Setup
# Last Updated: 2025-11-19

# ============================================================
# OPTION 1: COOKIE-BASED PERSISTENCE (Simple)
# ============================================================

# Method A: Application-Generated Cookies
# Backend generates JSESSIONID, LB uses it for routing

Load Balancer Configuration (NGINX):
  upstream backend {
    server backend1.example.com weight=1;
    server backend2.example.com weight=1;
    server backend3.example.com weight=1;

    sticky cookie JSESSIONID expires=1h domain=.example.com path=/ secure httponly;
  }

How It Works:
  1. Client connects to LB (no JSESSIONID cookie)
  2. LB routes to Backend A (round robin or random)
  3. Backend A creates session and returns: Set-Cookie: JSESSIONID=abc123
  4. Client stores cookie
  5. Next request includes: Cookie: JSESSIONID=abc123
  6. LB reads cookie, routes to Backend A (same backend)
  7. Session maintained across requests

Cookie Format:
  JSESSIONID=abc123.node1
  JSESSIONID=xyz789.node2

Advantages:
  + Application-native
  + Works across multiple load balancers
  + Cookie expires naturally
  + No LB state needed

Disadvantages:
  - Session lost if cookie deleted
  - Doesn't work with non-HTTP protocols
  - Can be cookie-blocked

# ============================================================
# OPTION 2: LOAD BALANCER INSERTED COOKIES
# ============================================================

# Method B: LB-Generated Persistence Cookie

Load Balancer Configuration (HAProxy):
  backend web_backend
    balance roundrobin
    cookie JSESSIONID insert indirect nocache

    server web1 192.168.1.10:80 check cookie web1
    server web2 192.168.1.11:80 check cookie web2
    server web3 192.168.1.12:80 check cookie web3

How It Works:
  1. Client first request (no persistence cookie)
  2. HAProxy selects Backend B
  3. HAProxy inserts: Set-Cookie: JSESSIONID=web2
  4. Client stores cookie
  5. Next request includes: Cookie: JSESSIONID=web2
  6. HAProxy decodes cookie, routes to web2 (Backend B)
  7. Session affinity maintained

Cookie Encoding:
  Plain: JSESSIONID=web2
  Encoded: JSESSIONID=d2ViMg== (base64)
  Encrypted: JSESSIONID=[encrypted_backend_id]

Advantages:
  + LB controlled
  + Works with any application
  + Fine-grained timeout
  + Can include failover info

Disadvantages:
  - Extra cookie in requests
  - Session lost if cookie deleted
  - LB must maintain cookie mapping
  - Requires cookie parsing

# ============================================================
# OPTION 3: SOURCE IP HASH (Stateless)
# ============================================================

# Method C: Route based on client IP address

Load Balancer Configuration (NGINX):
  upstream backend {
    ip_hash;  # Hash on client IP

    server backend1.example.com;
    server backend2.example.com;
    server backend3.example.com;
  }

Load Balancer Configuration (HAProxy):
  backend web_backend
    balance source  # Source IP hash

    server web1 192.168.1.10:80 check
    server web2 192.168.1.11:80 check
    server web3 192.168.1.12:80 check

How It Works:
  1. Client IP: 203.0.113.50
  2. hash(203.0.113.50) % 3 = 1
  3. Always routes to Backend 2
  4. Session maintained as long as client IP doesn't change

Hash Calculation:
  hash_value = crc32(client_ip) or md5(client_ip)
  backend_index = hash_value % number_of_backends
  select backends[backend_index]

Advantages:
  + Stateless (no LB state)
  + No cookies needed
  + Works with all protocols
  + Automatic and transparent

Disadvantages:
  - Unfair if clients share IP (NAT)
  - No persistence if client IP changes
  - Cannot add/remove servers without remapping
  - Hash collisions possible

Use Cases:
  - Database connections
  - P2P applications
  - VPN clients (static IP)
  - Mobile users (avoid if possible)

# ============================================================
# OPTION 4: DISTRIBUTED SESSION STORE (Recommended)
# ============================================================

# Method D: Centralized session storage (Redis/Memcached)

Architecture:
  Clients
     ↓
  Load Balancer
     ↓
  Backend Servers
     ↓
  [Shared Session Store: Redis Cluster]

Backend Configuration (Java + Spring):
  # Dependency: spring-session-data-redis
  @Configuration
  @EnableRedisHttpSession(maxInactiveIntervalInSeconds = 1800)
  public class SessionConfig {
    // Redis session store configured
  }

Backend Configuration (Node.js + Express):
  const session = require('express-session');
  const RedisStore = require('connect-redis').default;
  const { createClient } = require('redis');

  const redisClient = createClient();

  app.use(session({
    store: new RedisStore({ client: redisClient }),
    secret: 'secret-key',
    resave: false,
    saveUninitialized: false,
    cookie: {
      secure: true,
      httpOnly: true,
      maxAge: 1000 * 60 * 60 * 24  // 24 hours
    }
  }));

How It Works:
  1. Client connects to Backend A
  2. User logs in, session created
  3. Session stored in Redis with key: sessionid_abc123
  4. Cookie returned: SESSIONID=abc123
  5. Client connects (LB routes to Backend B)
  6. Backend B reads SESSIONID cookie
  7. Backend B retrieves session from Redis
  8. Session continues seamlessly

Redis Configuration:
  # Master-Slave replication for HA
  Redis Master: 192.168.1.40:6379 (writes)
  Redis Slave 1: 192.168.1.41:6379 (reads)
  Redis Slave 2: 192.168.1.42:6379 (reads)

  # Or use Redis Cluster for sharding
  Node 1: 192.168.1.40:6379
  Node 2: 192.168.1.41:6379
  Node 3: 192.168.1.42:6379

Advantages:
  + Survives backend failure
  + Can add/remove backends transparently
  + Consistent session across LBs
  + Zero downtime deployments
  + Can expire old sessions

Disadvantages:
  - Requires external service
  - Additional latency (Redis lookups)
  - Data persistence concerns
  - More complex setup

# ============================================================
# SESSION TIMEOUT CONFIGURATION
# ============================================================

Idle Timeout (30 minutes typical):
  Load Balancer (cookie):
    Expires: 30 minutes from last activity
    If no request for 30 min → session expires

  Redis Session Store:
    TTL: 1800 seconds (30 minutes)
    SETEX sessionid_abc123 1800 session_data
    After 30 min idle → key expires automatically

Absolute Timeout (8 hours typical):
  Session created: 09:00 AM
  Session expires: 05:00 PM (even if actively used)

  Implementation:
    Store creation_time with session
    Check: current_time - creation_time > 8 hours
    If yes: Force re-login

# ============================================================
# GRACEFUL HANDLING OF SESSION LOSS
# ============================================================

Scenario: Backend Server Failure

Without Session Replication:
  Client → LB → Backend A (DOWN)
           ↓
         Backend B (new session)
  Result: User logged out, must re-login

With Session Replication:
  Client → LB → Backend A (DOWN)
           ↓ (detect failure)
           → Backend B (fetch session from Redis)
  Result: User continues transparently

Implementation:
  # On backend startup
  app.use((req, res, next) => {
    if (!req.session.userId && req.session.previousUserId) {
      // Session recovered from store
      req.session.userId = req.session.previousUserId;
    }
    next();
  });

# ============================================================
# BEST PRACTICES
# ============================================================

1. Use Distributed Session Store
   - Most reliable approach
   - Handles all failure scenarios
   - Transparent to users

2. Secure Session Cookies
   - HttpOnly: Prevents JavaScript access
   - Secure: HTTPS only transmission
   - SameSite: CSRF protection

3. Monitor Session Activity
   - Track active sessions
   - Monitor session creation rate
   - Alert on unusual patterns

4. Regular Testing
   - Test backend failure scenarios
   - Verify session recovery
   - Test timeout behavior

5. Documentation
   - Document session strategy
   - Clear failover procedures
   - Monitoring/alerting setup

# EXAMPLE: COMPLETE REDIS SESSION SETUP
# ============================================================

Services:
  - Redis Cluster (3 nodes)
  - Load Balancer (2 nodes HA)
  - Backend Application (5 instances)

Redis Cluster Initialization:
  Node 1: redis-server --port 6379 --cluster-enabled yes
  Node 2: redis-server --port 6380 --cluster-enabled yes
  Node 3: redis-server --port 6381 --cluster-enabled yes

  # Create cluster
  redis-cli --cluster create 192.168.1.40:6379 192.168.1.41:6380 192.168.1.42:6381

Load Balancer (Session-aware):
  upstream app_backend {
    least_conn;
    server backend1:3000;
    server backend2:3000;
    server backend3:3000;
  }

  server {
    location / {
      proxy_pass http://app_backend;
      proxy_set_header X-Real-IP $remote_addr;
    }
  }

Application Connection String:
  redis://192.168.1.40:6379,192.168.1.41:6380,192.168.1.42:6381

Monitoring:
  - Redis cluster health: redis-cli cluster info
  - Session count: redis-cli DBSIZE
  - Memory usage: redis-cli INFO memory
  - Session expiry: monitor TTL values
