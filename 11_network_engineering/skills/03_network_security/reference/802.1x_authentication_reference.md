# 802.1X Authentication Reference

## Overview

Comprehensive guide to IEEE 802.1X port-based network access control, including authentication mechanisms, deployment strategies, and best practices.

## 802.1X Fundamentals

### Definition
- **Standard**: IEEE 802.1X-2010 (Port-Based Network Access Control)
- **Purpose**: Control access to network resources based on port authentication
- **Scope**: Layer 2 (Ethernet switches) and wireless
- **Framework**: Based on EAP (Extensible Authentication Protocol)

### Model Components

```
┌─────────────────┐
│    Supplicant   │  (User/Device/Client)
│  (Client)       │  - Provides credentials
└────────┬────────┘  - Requests network access
         │
         │ EAP Frames
         ▼
┌─────────────────┐
│   Authenticator │  (Switch/Access Point)
│  (Switch/AP)    │  - Enforces port state
└────────┬────────┘  - Forwards EAP frames
         │
         │ RADIUS Protocol
         ▼
┌─────────────────┐
│ Authentication  │  (RADIUS Server)
│    Server       │  - Validates credentials
│  (RADIUS)       │  - Grants/denies access
└─────────────────┘
```

### Port States

#### Unauthorized State (Before Authentication)
```
Supplicant: Cannot transmit
- Only EAP frames accepted
- All other frames dropped
- No network access

Authenticator: Block traffic
- Forward EAP frames only
- Drop all other traffic
- Port not operational
```

#### Authorized State (After Successful Authentication)
```
Supplicant: Full access
- All frames transmitted normally
- Network access granted
- Session active

Authenticator: Allow traffic
- Forward all frames
- Port fully operational
- Session active
```

## EAP (Extensible Authentication Protocol)

### EAP Packet Structure
```
Frame Format:
┌────────┬─────────┬──────────┬────────┐
│ Code   │ ID      │ Length   │ Data   │
│ (1B)   │ (1B)    │ (2B)     │ (var)  │
└────────┴─────────┴──────────┴────────┘

Code Values:
- 1: Request
- 2: Response
- 3: Success
- 4: Failure

Data Contains:
- Authentication information
- Protocol-specific data
- Message exchange details
```

### EAP Exchange Process

```
1. Supplicant waits for EAP Request
   (or sends EAPOL Start)

2. Authenticator sends EAP Request/Identity
   └─ Asks "Who are you?"

3. Supplicant responds with EAP Response/Identity
   └─ Provides username

4. Authenticator forwards to RADIUS server
   └─ Via RADIUS Access-Request

5. RADIUS server challenges supplicant
   └─ Via EAP method exchange

6. Supplicant responds with credentials
   └─ Encrypted according to method

7. RADIUS server validates
   └─ If valid: RADIUS Access-Accept
   └─ If invalid: RADIUS Access-Reject

8. Authenticator enforces decision
   └─ Success: Port authorized
   └─ Failure: Port unauthorized
```

## EAP Methods

### EAP-TLS (Transport Layer Security)

**Characteristics**
- **RFC**: RFC 2716
- **Security**: Strongest among EAP methods
- **Authentication**: Mutual (both sides verify)
- **Certificates**: Required for both client and server
- **Overhead**: High (certificate exchange)

**Implementation**
```
Server Certificate:
- Issued by trusted CA
- Valid domain name
- Used to authenticate server
- Client verifies certificate

Client Certificate:
- Installed on client device
- Issued by organization CA
- User identity in certificate
- Server verifies certificate

Advantages:
✓ Mutual authentication
✓ Strong cryptography
✓ Perfect forward secrecy
✓ Phishing resistant
✓ Not password-based

Disadvantages:
✗ Requires certificate infrastructure
✗ Certificate deployment effort
✗ Certificate renewal management
✗ Client support variations
```

**Deployment**
```
1. Create/purchase internal CA
2. Generate server certificate
3. Deploy RADIUS server certificate
4. Create client certificate templates
5. Issue certificates to users/devices
6. Deploy certificates to endpoints
7. Configure RADIUS server
8. Configure 802.1X on switches
9. Configure clients with certificate
10. Test and troubleshoot
```

### EAP-TTLS (Tunneled TLS)

**Characteristics**
- **RFC**: RFC 5281
- **Security**: Strong, uses TLS tunnel
- **Authentication**: Server only (one-way)
- **Inner Method**: Various options
- **Legacy Support**: Good

**Inner Authentication Methods**
```
- Password Authentication Protocol (PAP)
  └─ Password over encrypted tunnel
  └─ Better than plaintext

- Challenge Handshake (CHAP)
  └─ Challenge-response over tunnel
  └─ Hash-based

- MS-CHAPv2
  └─ Microsoft version of CHAP
  └─ Common in Windows environments

- None (Inner EAP)
  └─ Another EAP method inside tunnel
  └─ Can use EAP-TLS or others
```

**Advantages**
- Doesn't require client certificates
- Works with password authentication
- Good legacy device support
- Server certificate only

**Disadvantages**
- Less secure than EAP-TLS
- Password-based (if using PAP/CHAP)
- Potential phishing if server cert not validated

### PEAP (Protected EAP)

**Characteristics**
- **RFC**: RFC 5422
- **Creator**: Cisco, Microsoft, RSA
- **Security**: Strong, TLS tunnel
- **Authentication**: Server only
- **Inner Method**: Flexible

**Common Inner Methods**
```
PEAP/EAP-MSCHAPv2 (PEAPv0):
- Most common combination
- Windows native support
- Server verifies client password
- Client verifies server certificate
- Common in enterprise Windows

PEAP/EAP-TLS (PEAPv0):
- EAP-TLS inside PEAP tunnel
- Double encryption
- Certificate inside encrypted tunnel
- Extra security but overhead

PEAP/EAP-GTC (PEAPv0):
- Generic Token Card inside PEAP
- Supports OTP and tokens
- Less common
```

**Advantages**
- Wide support (Windows, iOS, Android, Linux)
- No client certificates required
- Server authentication
- Good for mixed environments

**Disadvantages**
- Password-based vulnerable
- Server-only authentication
- Not as strong as mutual auth methods

### EAP-FAST (Flexible Authentication via Secure Tunneling)

**Characteristics**
- **RFC**: RFC 4851
- **Creator**: Cisco
- **Security**: Good, TLS tunnel
- **Authentication**: Server only
- **Key Feature**: PAC (Protected Access Credential)

**PAC (Protected Access Credential)**
```
First-time authentication:
1. Client connects
2. Authenticator/RADIUS sends PAC
3. Client stores PAC securely
4. Mutual authentication happens
5. Session created

Subsequent authentication:
1. Client connects
2. Presents stored PAC
3. Quick mutual authentication
4. Session created
5. PAC can be refreshed
```

**Advantages**
- Fast resume (via PAC)
- No client certificates
- Good for mobile devices
- Server-side PAC storage option

**Disadvantages**
- Cisco proprietary (though RFC)
- Less common than PEAP
- PAC management complexity

### EAP-GPSK (Generalized Pre-Shared Key)

**Characteristics**
- **RFC**: RFC 5740
- **Authentication**: Mutual
- **Key Material**: Pre-shared key
- **Modern**: Yes

**Use Cases**
- Device authentication
- Key derivation
- Mutual authentication with PSK

## RADIUS Integration

### RADIUS Protocol
```
RADIUS Packet Types:
- Access-Request (Client → Server)
- Access-Accept (Server → Client)
- Access-Reject (Server → Client)
- Accounting-Request
- Accounting-Response
```

### RADIUS Attributes

```
Key Attributes:
- User-Name: Username
- User-Password: Encrypted password
- NAS-IP-Address: Switch/AP IP
- NAS-Port: Port number
- Service-Type: Type of service
- Framed-IP-Address: Assigned IP
- Reply-Message: Message to user
- Tunnel-Type: Tunneling protocol
- Tunnel-Medium-Type: Medium type
- Tunnel-Private-Group-ID: VLAN ID
- Filter-Id: ACL name
```

### VLAN Assignment via RADIUS

```
Tunnel-Type = VLAN
Tunnel-Medium-Type = 6 (802)
Tunnel-Private-Group-ID = 100

Result: Supplicant assigned to VLAN 100

Example with ACL:
Filter-Id = ALLOW_WEB_ONLY
Tunnel-Private-Group-ID = 20

Result: Port assigned to VLAN 20 with ACL applied
```

## Deployment Models

### Model 1: Switch-based Authentication

```
Supplicant (Device)
       │ EAP Frames (802.1X)
       ▼
Switch Port (Authenticator)
       │ RADIUS Protocol
       ▼
RADIUS Server (Authentication)
       │ Accept/Reject
       ▼
Switch Port (Enforces authorization)

Use Case: Wired network access control
```

### Model 2: Access Point (Wireless)

```
Supplicant (Wireless Device)
       │ EAP Frames (over EAPOL)
       ▼
AP/Wireless Controller
       │ RADIUS Protocol
       ▼
RADIUS Server
       │ Accept/Reject
       ▼
AP (Authorizes wireless connection)

Use Case: Wireless network access control
```

### Model 3: Controller-based

```
Supplicant
       ▼
AP (Authenticator)
       │
       ▼
Wireless Controller
       │
       ▼
RADIUS Server
       │
       ▼
Controller (Enforces policy)

Use Case: Large wireless deployments
```

## 802.1X Configuration Examples

### Cisco Switch Configuration

```
! Enable 802.1X globally
aaa new-model
aaa authentication dot1x default group radius
aaa authorization network default group radius
dot1x system-auth-control

! Configure RADIUS server
radius server RADIUS_SERVER
 address ipv4 10.1.50.10 auth-port 1812 acct-port 1813
 key 0 SuperSecretKey123!

! Configure interface for 802.1X
interface GigabitEthernet0/0/1
 description User Port - 802.1X Enabled
 switchport mode access
 switchport access vlan 10

 ! Enable 802.1X
 dot1x pae authenticator
 dot1x port-control auto

 ! Re-authentication timer
 dot1x reauthentication enable
 dot1x timeout reauth-period 3600

 ! Timeout settings
 dot1x timeout tx-period 30
 dot1x timeout quiet-period 60

 ! Guest VLAN (optional)
 dot1x guest-vlan 999

 ! Unauthorized ACL
 access-class 100 in

 ! Port security (optional)
 switchport port-security
 switchport port-security mac-address sticky

! Verify configuration
show dot1x interface GigabitEthernet0/0/1
show dot1x statistics interface GigabitEthernet0/0/1
show authentication sessions interface GigabitEthernet0/0/1
```

### Windows RADIUS Server Configuration

```PowerShell
# Install RADIUS service
Install-WindowsFeature NPAS -IncludeManagementTools

# Configure RADIUS clients (switches/APs)
Add-NpsRadiusClient -Address 10.0.0.5 `
  -Name "Building-A-Switch" `
  -SharedSecret "SuperSecretKey123!"

# Create authentication policy
$AuthPolicy = New-NpsNetworkPolicy -Name "802.1X_Users" `
  -State Enabled `
  -ProcessingOrder 1 `
  -Type Access

# Configure conditions
Set-NpsNetworkPolicyCondition -PolicyName "802.1X_Users" `
  -ConditionType NASPortType `
  -ConditionValue Ethernet

# Configure EAP method
Add-NpsRadiusServerGroupServer -RadiusServerGroupName "Internal" `
  -RadiusServerName "RADIUS-Server1"
```

### Linux FreeRADIUS Configuration

```bash
# Install FreeRADIUS
apt-get install freeradius

# Configure RADIUS clients (clients.conf)
cat >> /etc/freeradius/3.0/clients.conf << 'EOF'
client Building-A-Switch {
    ipaddr = 10.0.0.5
    secret = SuperSecretKey123!
    shortname = building-a-switch
}
EOF

# Configure users (users file)
cat >> /etc/freeradius/3.0/users << 'EOF'
testuser Password.1 {
    Tunnel-Type = VLAN,
    Tunnel-Medium-Type = IEEE-802,
    Tunnel-Private-Group-ID = 100
}
EOF

# Start FreeRADIUS
systemctl start freeradius
systemctl enable freeradius
```

## Client Configuration

### Windows Configuration

```
Settings → Network & Internet → WiFi (or Ethernet)
→ Change adapter options
→ Right-click → Properties
→ Authentication tab
→ Enable 802.1X
→ Select PEAP or EAP method
→ Configure server certificate validation
→ Enter username/password or certificate
```

### macOS Configuration

```
System Preferences → Network → WiFi (or Ethernet)
→ Advanced → Security tab
→ 802.1X
→ Enable 802.1X
→ Select PEAP/TTLS/TLS
→ Enter credentials
→ Trust certificates as needed
```

### Linux Configuration

```
wpa_supplicant configuration:
ctrl_interface=/var/run/wpa_supplicant
network={
    ssid="Corporate Network"
    key_mgmt=IEEE8021X
    eap=PEAP
    identity="username"
    password="password"
    phase1="peapver=0"
    phase2="auth=MSCHAPV2"
}
```

## Best Practices

### Security
- Use EAP-TLS for highest security
- Validate server certificates
- Require strong passwords
- Implement certificate pinning
- Rotate credentials regularly
- Use MFA when possible

### Operational
- Plan certificate infrastructure
- Test in lab before deployment
- Provide guest VLAN
- Document configuration
- Monitor authentication logs
- Set up alerting

### Troubleshooting
- Enable detailed logging
- Check RADIUS communication
- Verify certificate validity
- Test with different clients
- Monitor supplicant logs
- Check switch/AP logs
